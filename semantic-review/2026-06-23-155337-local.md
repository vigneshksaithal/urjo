# Removal of `twice_daily` post frequency and `speed_window` scheduler slot

The change eliminates the middle posting-frequency tier (`twice_daily`) and the dedicated 08:00 UTC speed window slot. The scheduler now fires at 16:00 (`daily_puzzle`) and 23:00 (`evening_puzzle`) only, and the supported frequencies jump directly from `once_daily` to `thrice_daily`. All call sites, the cron schedule, and tests are updated consistently.

**Watch for:** Subreddits that already have `postFrequency: 'twice_daily'` stored in Redis will be silently downgraded to `'once_daily'` on the next read (confirmed — `parseConfig` falls through to the default with no log, no error, no write-back).

---

## High-level view

The removals are mechanically complete: type union, validator allowlist, slot mapper, title builder, cron schedule, and tests all move in lockstep. Nothing is left referencing `speed_window` or `twice_daily` in the source tree.

The one unaddressed risk is the live Redis state. `parseConfig` treats any unrecognized `postFrequency` value as a new install and falls back to the default — after this deploy that means `once_daily`. Subreddits configured at `twice_daily` will silently lose their evening post slot with no observable signal anywhere.

The `PostFrequency` union now has a gap (`once_daily | thrice_daily`) with no comment explaining the missing middle value. That's a future-maintainer hazard if `twice_daily` is ever reconsidered.

### Silent downgrade for existing `twice_daily` subreddits

`parseConfig` validates `postFrequency` against `VALID_FREQUENCIES` and falls back to `DEFAULT_CONFIG.postFrequency` when the stored string isn't recognized:

```typescript
postFrequency: frequency !== undefined && (VALID_FREQUENCIES as readonly string[]).includes(frequency)
    ? frequency as PostFrequency
    : DEFAULT_CONFIG.postFrequency,
```

After this deploy, `VALID_FREQUENCIES` is `['once_daily', 'thrice_daily']`. Any subreddit Redis hash still containing `postFrequency = twice_daily` reads back as `once_daily` — without writing the corrected value, without logging the downgrade, and without surfacing anything to the subreddit mod. Those communities stop receiving their evening puzzle slot silently.

A minimal fix is a one-time migration script, or at least a structured log line distinguishing "unrecognized value, fell back to default" from "no config stored, created defaults."

### `PostFrequency` gap

`isGrowthPostSlotEnabled` is correctly simplified to two active paths. The concern is forward-looking: the union `'once_daily' | 'thrice_daily'` has no comment explaining why `twice_daily` is absent. If it comes back, a developer might add it without knowing it was intentionally removed — or worse, re-wire it to the wrong slot.

### Test coverage gap at runtime

The existing `updateSubredditConfig ignores invalid postFrequency` test covers the `parseConfig` fallback path generically, which is sufficient for the parsing logic itself. What the test suite can't exercise is the rollout scenario where live Redis data contains `twice_daily` and the scheduler fires — that's a production-only risk that the review should acknowledge rather than defer.

</details>
